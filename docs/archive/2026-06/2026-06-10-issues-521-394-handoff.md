### Two findings posted → https://github.com/jackli921/kuruma-rental/issues/521#issuecomment-4676004224
- 🔴 **Plaintext invite token** — `0048` stores `token text UNIQUE` (raw bearer credential for operator access). Fix: store `sha256(token)` only, show plaintext once at creation, look up by hash.
- 🟡 **Non-atomic 3-write grant** — `provider-access.ts` runs `memberships.create → invites.markAccepted → users.setOperatorAccess` with no transaction; partial failure locks the user out despite a grant, and the step-1 short-circuit doesn't self-heal. Fix: wrap in raw `runTx`, or make the short-circuit re-assert `setOperatorAccess`.

## #394 — location search with hierarchical region taxonomy (NEXT — scoped, not planned)

- **Issue:** #394 (OPEN, P2). Design is already decided in the issue body: **Approach A** — `regions` tree + `locations.region_id` + filter by node + recursive descendants. Lat/lng (added in `0045`, seeded) is the deferred Approach-B hook.
- **Why now:** this morning's investigation confirmed area search **does not exist today** — search is date+class only; the landing location field is a static `{/* Location (static) */}` placeholder (`vite/landing/SearchWidget.tsx:34`). #394 is the real MVP gap and is independent of auth/#521 and of #531.

### Verified code facts (against `marketplace-pivot`)
- `regions` / `region_id` **do not exist yet** (grep empty).
- `locations` table defined at `packages/shared/src/db/schema.ts:198`; seeded with Osaka-area rows (Namba, Shin-Osaka, KIX, Umeda, Tennoji, Kobe, Kyoto, Nara, Osaka Castle) in `seed-data/locations.ts`, **with real lat/lng**.
- Renter search today: `from`/`to` + `class[]` only; `pickupLocationId` only via storefront-card clicks. Form `vite/storefronts/StorefrontSearchForm.tsx`; params `vite/storefronts/params.ts`; route `routes/$locale/search.tsx` (`validateSearch` = from/to/pickupLocationId/class/view); API `vite/search/api.ts` + `vite/storefronts/api.ts` → `/search/vehicles` + `/storefronts/search`. **No geo filter in API** (`services/flat-search.ts`, `storefront-search.ts`).
- **Operator location form is FROZEN Next.js** — `packages/web/src/modules/locations/components/LocationForm.tsx`, `app/[locale]/(business)/manage/locations/page.tsx`. The Vite app has **no** `/manage` location route (only `_business/dashboard` stub). So the AC item "operator portal location form has a region picker" is **blocked** on the operator-portal Vite migration (does not exist; cf. #504).

### Open decisions to settle before planning (ask the user)
1. **Tree model:** adjacency list (`parent_id` self-ref) + Postgres `WITH RECURSIVE` CTE (recommended — native, simple at this scale) vs materialized path.
2. **`locations.region_id` NOT NULL backfill:** AC wants NOT NULL, but seeded/existing locations have none. Plan: add nullable → seed `regions` → backfill existing rows → set NOT NULL (multi-step in one slice). Confirm acceptable.
3. **Operator region picker UI = defer.** Recommend: first slice = `regions` table + seed + backfill + **renter** cascading search; make `region_id` settable via the locations API (no operator UI). Operator picker waits for operator-portal Vite migration (don't build new UI in the frozen Next.js app). Confirm.
4. **Seed scope:** issue says Osaka+Kyoto+Tokyo min; must at minimum cover existing seeded locations (Osaka areas, Kyoto, Hyogo/Kobe, Nara).
5. **Where dropdowns live:** landing `SearchWidget` (replace the static placeholder) + `/search` form; wire `regionId` into search params/URL/loader (mind #499 filter-state preservation).

### Recommended first slice (vertical)
`regions` table + Osaka/Kyoto/Hyogo/Nara seed + `locations.region_id` backfill → API `regionId` filter (recursive-descendant CTE in `flat-search`/`storefront-search`) → renter cascading dropdowns (landing + /search) wired through params. Migration ≈ `0049` (parallel session took `0048`; **do not hardcode**, renumber per the drizzle gotcha; #511/#512 also active).
